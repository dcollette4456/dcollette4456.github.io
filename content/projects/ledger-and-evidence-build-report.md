Session notes, not a spec. Written for tracking what got done, where the two governing documents and the implementation disagreed, and what still stands between this and an actually automated intel-analyst workflow. Everything below happened; nothing is aspirational.

Branch: `claude/article-classification-system-i4nztf`, 11 commits, not yet merged to `main`. **Nothing in this report is live on the deployed site yet** — see Housekeeping at the bottom.

## What got built

Working from `CLAUDECODEBRIEF_ledger_and_evidence.md`, an implementation brief, against both governing specs, in the order the brief itself suggested, stopping after each step to show output before continuing.

**Serial ledger.** `/data/serials.json` moved from a flat array of strings to a versioned, per-entry object (schema, timestamp, title, path, issue number, both spec versions, authoring method, status, a `collision` field). Migrating it surfaced a real bug: the old flat ledger was missing `TI-20260817-001` (the PRC issue) entirely — a serial that had been published for two weeks with nothing checking it was recorded anywhere. A CLI (`scripts/allocate_serial.py`) now allocates the next serial for a date and appends it, which is the actual fix for the collision problem this brief exists because of.

**Four JSON Schemas.** `serials-1.json`, `registry-2.json`, `manifest-1.json`, `ledger-4.json`, each versioned and kept forever per the brief's own rule. A small, dependency-free validator (`scripts/validate_data.py`, hand-rolled against the narrow subset of JSON Schema these four files actually use) runs all of them, wired into CI on every push and pull request.

**Source registry.** 63 sources, every one cited across the References section of all 8 published issues, registered in the **backfill pool only** — never live, since no claim has been graded from any of them. Each carries a real admission record, including a working impersonation check (edit distance plus a same-stem-different-TLD-or-hyphenation test against every prior canonical domain), not a stub. Zero holds on the actual backfill; verified separately against a synthetic typosquat and a hyphenation variant, both caught.

**Evidence manifests.** All 90 unique URLs cited across the 8 issues fetched, hashed (raw and normalized, per the `html/v1` normalizer), and submitted to archive.org, from the user's own machine — this session's network is allowlisted to a handful of domains and cannot reach the open web, confirmed with `curl` before writing any data rather than fabricating fetch results. Of 90 URLs, 1 could not be fetched by any method available; of the rest, 19 archive.org submissions succeeded and 71 were rate-limited or failed outright, which is disclosed on every entry rather than hidden — attestation (the hashes) happened regardless, per the rule that attempting preservation is required and succeeding is not. Every issue's manifest hash now prints in its footer, read live from `/data/evidence/` at build time.

**Standing source list, `/coverage/vocab/`, `/coverage/standing/`.** The standing list ships empty and says so honestly: nothing in this project's history has ever run an actual sweep against a published list, so backfilling one would misstate a discovery process that never happened. Five vocabulary files (telemetry classes, sectors, source types, the six-grade scale, and a provisional hunt-stage list, flagged as unverified against its own source document) are published and rendered.

**Claim ledger writer.** `scripts/claim_writer.py` mechanizes the deterministic half of grading — the gates, the fingerprint, the assertion license — and leaves the judgment half (segmentation, hunt-value mapping, grader identity) as required input rather than guessing at it. Verified against 8 hand-computed cases covering every grade path, plus an end-to-end run reproducing the classification spec's own worked PLC-injection example exactly. No claim has been written with it against a real issue, on purpose: the brief is explicit that reverse-engineering claims from finished prose is fabrication with extra steps.

**Claim resolver, entity pages, export routes.** `/claims/` and `/entities/` render an honest account of why nothing resolves yet. `/data/export/sources.json` is real, regenerating from the live registry at every Hugo build. `/data/export/claims.jsonl` is a verified, working template currently producing zero lines against the real, empty ledger.

**Both governing specs updated.** `Classification_System_v4-1_Spec.md` → **v4.2**, `Article_and_Site_Design_Specification_v2-8.md` → **v2.9**, delivered as files rather than committed, documenting all of the above in each document's own established changelog format.

## Conflicts, and how each was resolved

**`serials.json`'s shape.** The brief's own example schema for the serial ledger was a rich per-entry object. Classification spec §14's storage-layout diagram described the same file as "a flat list of issued serials." Per the brief's own rule — where the brief and a spec disagree, the spec wins, and say so rather than resolving it silently — this should have been a stop. It wasn't caught until after the migration had already shipped. Resolved by disclosing the discrepancy explicitly in the commit and, later, correcting the classification spec itself in v4.2: a flat list cannot record a `collision` field, a status, or a title, all of which the brief's own requirements (and, on inspection, classification spec §15's own text) actually need. The spec's storage-layout section was describing a stub that predated this build, not a considered decision to keep the file flat forever.

**`/actors/[cluster]/` versus `/entities/[type]/[id]/`.** The article spec proposed a dedicated route for cluster (actor) pages, separate from the entity pages for families, tools, campaigns, and vulnerabilities. The classification spec's own findability section already describes clusters as one of five entity types under one unified system. Building against a real implementation deadline, the unified `/entities/` structure is what got built, matching the classification spec's language. **Not silently decided.** Flagged explicitly in the v2.9 update, with a recommendation to retire the `/actors/` row, but left as an open decision for a person to make on purpose — nothing is broken today because no cluster page exists yet either way, but it should be settled before one does.

**The evidence-capture bug.** `capture_evidence.py`, as first written, skipped archive.org submission entirely whenever the direct fetch got a non-2xx status or failed outright. This produced `archive.status: not_attempted` on 8 entries, which the brief's own build-time validation rules treat as a hard block (`unavailable` is a legal disclosure; `not_attempted` means the capability existed and wasn't used, which is a defect). The validator caught its own output being wrong. Fixed to always attempt archive submission — archive.org does its own independent fetch, so a local 403 or a local timeout says nothing about whether archive.org can reach the same URL — and re-run. Cost: two full network passes from the user's machine and one round where the fix was pushed but not yet pulled before the re-run happened, so the second run used the still-broken script. Sequencing "pull the fix, verify it's there, then re-run" explicitly is what actually closed it on the third attempt.

**The dead `/coverage/` page.** While building `/claims/` and `/entities/`, both silently produced no HTML output at all — only an RSS index — with Hugo warning about a missing layout for `layout: "index"` on a section. Tracing it back, `/coverage/` itself, live since an early commit in this project's history, uses the identical pattern and has the identical problem, confirmed against two different modern Hugo versions. The one commit that built `/coverage/`'s landing page was, apparently, never rebuilt or checked again after that commit. Whether the live site was actually affected is unknown — the repository's checked-in `public/` directory isn't reliably kept in sync with real deploys — but it would have broken the next time CI built regardless of history. Fixed by switching all three routes to the `list.html` naming convention Hugo resolves by default, proven by the one new route (`/data/export/`) that had been built without the broken pattern in the first place.

**This session's own sandbox.** Evidence capture needs the open internet; this remote session's network is allowlisted to GitHub, npm, PyPI, and the Anthropic API. Resolved by handing the (tested, logic-verified) capture script to the user's own machine and coordinating the push/pull/rebase cycle from here, rather than fabricating fetch results to work around the constraint.

## What's still manual before this is actually automated

In roughly the order it would need to happen, not in order of difficulty.

**No sweep exists.** The standing source list is real infrastructure with nothing in it. Nothing fetches new source material on a schedule, checks it against the standing list's discovery rules (`standing`/`followed`/`supplied`), or decides what's in-window for a live issue. *Suggested:* a scheduled job (the site already has a GitHub Actions workflow; this is the natural place) that sweeps the standing list, records what it found per source, and stages a pool for review before any drafting starts.

**No grading pipeline.** `claim_writer.py` computes grade, fingerprint, and assertion license from a completed set of gate answers someone already worked out. Nothing reads a fetched document and produces those gate answers — that's a model's job, and no model is in this loop yet. Classification spec §30 requires three independent grading passes with an agreement check on top. *Suggested:* an orchestrated multi-pass grading step (three separate model calls against the same document, majority-or-conservative resolution per classification spec §15) that emits the gate-answer JSON `claim_writer.py` already knows how to consume. The mechanical half is done; the judgment half needs a model wired to it.

**No reconciliation.** The spec calls the prose-versus-ledger reconciliation pass one of the few checks that structurally needs a model rather than a string comparison, with its own three-pass agreement rule. Nothing implements it. *Suggested:* build this alongside the grading pipeline above, since it consumes the same kind of independent-pass infrastructure — a check that compares drafted prose against `segmentation.assertions` and blocks on drift, per classification spec §15 and §30.

**No entity resolution.** `/data/entities/` exists with real schemas and zero logic to populate them. Classification spec §10's stated-equivalence rule (when two sources' names for something are the same entity) is not implemented anywhere. *Suggested:* this is naturally a byproduct of the grading pipeline above, not a separate system — entity mentions come out of the same per-document read that produces gate answers, and can populate the entity files as a side effect of grading, gated on the same stated-equivalence rule.

**Archive capture succeeds a fifth of the time.** 19 of 90 this run, mostly to rate limiting on a free, anonymous, ninety-requests-in-one-run submission pattern. This is disclosed correctly today, which is the right floor, but it's a low ceiling. *Suggested:* either an archive.org API key (raises the rate limit substantially), a second provider attempted on failure per classification spec §14's own "where the first provider fails, a second is attempted" rule (currently only one provider is wired), or simply spacing submissions across a longer window than one sitting.

**`issueNumber` is still hand-typed.** Both specs say it should be Hugo-derived from publication order, never authored. In practice every published issue has it hardcoded in front matter. *Suggested:* either build the Hugo-side derivation the specs already describe, or formally amend the specs to say hand-authored issues assign it at commit the same way the serial now does, since that's what's actually happening.

**Front matter doesn't sync from the ledger.** Once a real claim ledger exists for an issue, fields like `clusters`, `sectors_confirmed`, and `claims_graded` still have to be hand-transcribed into front matter — nothing reads a completed ledger and emits them. *Suggested:* a small script, the same shape as `build_registry_backfill.py`, that takes a finished `/data/ledger/{serial}.json` and emits the pipeline-derived front matter block, so authoring against a real ledger doesn't regress into hand-transcription errors the same absent-not-fabricated rule exists to prevent.

**The visual queue is entirely manual.** Figure sourcing, self-hosting, and provenance tagging (`fetched` versus `supplied_verified`) have no tooling at all, just a documented process a person follows by hand.

**Two open design decisions, cheap to close, not yet closed.** The `/actors/` versus `/entities/` question above. And the `stage` vocabulary, published provisional because neither spec has ever transcribed the ODNI Common Cyber Threat Framework's actual stage list to check it against.

**This branch isn't merged.** See Housekeeping.

## Housekeeping

**A pull request is still needed.** Everything in this report lives on `claude/article-classification-system-i4nztf`, which sits cleanly ahead of `main` with no conflicts, but the site only deploys from `main`. None of the new routes, the registry, the evidence manifests, or the updated specs are live until this merges.

**A known date/serial inconsistency, left alone on purpose.** `russia-onboarding-trap.md` (`TI-20260822-001`) and `compile-to-compromise-rust-crate-kernel-driver.md` (`TI-20260822-002`) both carry front-matter `date:` fields one calendar day earlier than the date their own serial encodes. Caught while checking the *Roadblocks & Spec Gaps* write-up for a reported mismatch — that write-up itself turned out to be internally correct throughout, every reference to `TI-20260822-001` in it is consistent with the published issue. The actual discrepancy is inside the issues' own front matter, not the write-up. Deliberately not touched: editing a published issue's metadata, even a date field, is exactly the kind of after-the-fact change this whole system exists to make expensive and visible rather than cheap and silent. Noted here instead, the same way the DPRK/Iran timeline inconsistency was noted rather than silently reconciled in an earlier correction.
